# Uno Testing

The Uno App MCP lets you drive the real running app: launch it, read its visual tree, act on elements through automation peers, and check what actually rendered. Use it to prove a change works instead of inferring from source. The failure modes here are mostly timing and stale references, so the rules below are about when to refresh and when to wait.

## Prerequisite

Confirm the app tools exist before starting. Some clients list the `uno_app_*` tools directly; others list only `uno_health`, `uno_discover_tools`, and `uno_execute_tool`. In that case call `uno_discover_tools` to see the app tools and run each one as `uno_execute_tool(toolName: "uno_app_start", arguments: {...})`. If `uno_health` reports `toolCount: 0`, read its `issues` and `resolutionKind` before concluding anything. In `issues[].code`, `HostUnreachable` means the DevServer host is still connecting (wait a few seconds and call it again), and `NoSolutionFound` or `WorkspaceAmbiguous` means no Uno solution was found or selected under the workspace root (`resolutionKind` then reads `NoCandidates`, `NoValidWorkspace`, or `Ambiguous`; `uno_app_select_solution` picks one of `candidateSolutions`, or call `uno_app_initialize(workspaceDirectory, solutionPath)`). Only when the host is connected and discovery still returns no `uno_app_*` tools are the app tools not licensed on this machine: then tell the user to sign in to Uno Platform (the Uno Platform Studio window in their IDE). Licensing is per tool: a Community licence has a non-zero `toolCount` but lacks `uno_app_element_peer_action` and `uno_app_get_element_datacontext` (Pro or Business) and `uno_app_get_memory_counters` (Business); when discovery does not list them, use the fallbacks named in the steps below and report DataContext assertions as not run. In every case where the tools stay unavailable, and for Release builds, verify through the platform accessibility tree on Windows or Android (`references/without-app-mcp.md`); only where that is not possible either, fall back to static review of the XAML and Model code, labelled as unverified. Do not describe test results you did not obtain.

## Workflow

Verify behaviour on a Debug build with the App MCP. Use a Release build only when the task requires one (a spec that asks for it, or a Release-only defect such as trimming or AOT), and then drive it through the accessibility tree (`references/without-app-mcp.md`) instead of repeating every check with screenshots.

1. **Build, then start.** Make sure Hot Design will not open over the app (see the first critical rule). Build once with `dotnet build -f net10.0-desktop` (or the app's own TFM, read from `<TargetFrameworks>`) so compile errors surface as build output. Then `uno_app_start(projectPath, targetFramework, connectionTimeoutSeconds: 120)` with the full `.csproj` path. Skip the start if the user already has it running.
2. **Wait for the connection, then for Hot Reload; do not restart.** If the start times out, the app is usually still launching. Poll `uno_app_get_runtime_info` every few seconds and call `uno_devserver_diagnostics` if it keeps reporting no instance. Calling `uno_app_start` again kills the process and starts over. The start returns about 12 s before Hot Reload is live (measured through the App MCP host: the start returns 6 s after launch on desktop and 40 s on Android, and edits made 0 to 8 s later were dropped while an edit at 12 s applied), and a dropped edit is not replayed, so do not edit before Hot Reload is ready. When discovery lists `uno_app_hot_reload_status`, the start already waits for it and its result has a `Hot Reload:` line; if that line says it is still initializing, call `uno_app_hot_reload_status(waitForReady: true)` before the first edit. Without that tool, make the first edit of an existing `.xaml` or `.cs` file at least 15 s after the start returns: the indicator that would show readiness is hidden by the `UseStudio` arguments below, so the wait is by the clock.
3. **Baseline.** `uno_app_visualtree_snapshot(detail: "normal")` plus a screenshot saved with `path` before touching anything, so failures have a before/after. This is the one routine snapshot; from here on, locate and assert with `uno_app_find_elements`.
4. **Locate by selector; snapshot only to discover or assert.** Every element tool takes `automationId` (the XAML's `AutomationProperties.AutomationId`) or `name` (`x:Name` or `AutomationProperties.Name`) in place of `elementRef`, resolved against the live tree at call time: no snapshot first, nothing goes stale, and it survives navigation and hot reload. You know the ids from the XAML you wrote or read, so act straight away. Matching is exact and case-sensitive; 0 matches is an error naming the value, N matches is an error listing the candidates as snapshot lines with fresh handles (act on one by `elementRef`, or add `scopeRef` to search under one container). When no id or name exists, read the snapshot: each line is `Type ^handle #Name :line [patterns] "text"`; the handle is the bare token after `^` (`elementRef: "5k"` for `Button ^5k`, not `"^5k"`), and it dies with the next UI change.
5. **Act.** `uno_app_element_peer_default_action(automationId | name | elementRef)` always runs `invoke`, so use it only on `[i]` elements (`Button`, `HyperlinkButton`); on anything else it fails. For the other letters use `uno_app_element_peer_action(automationId | name | elementRef, action)`: `t` toggle, `x` expand/collapse, `s` select, `v` setValue (fills a `TextBox` without keyboard focus), `r` setRangeValue. `uno_app_type_text(text, automationId | name | elementRef)` focuses that control and types into it in one call. `ListViewItem` shows no letters on Uno, so select it by pointer or keyboard. Without `uno_app_element_peer_action` (Community), take an unscoped `detail: "full"` snapshot, `uno_app_pointer_click` the centre of the element's `@@x,y,w,h` bounds (that focuses a field or selects an item), then `uno_app_type_text(text, intervalInMs: 50)`; or Tab into the field with `uno_app_key_press`.
6. **Wait, then check, in one call.** `uno_app_find_elements(automationId | name | text | type, waitForMs: 2000)` re-checks the live tree every 100 ms until something matches (max 10 s) and returns only the matches: a count line, then one snapshot line per match with its `{state}`: `disabled`, `checked|unchecked|indeterminate`, `selected`, `expanded|collapsed`, `value=…`, `items=N`, `selectedIndex=N`, and `!hidden` when collapsed. That is the check after an action: the next page's title by `automationId`, the submit button no longer `{disabled}`, the list at `{items=12}`, the toggle `{checked}`, the error text by `text` with `textContains: true`. Zero matches is a result, not an error, so absence is asserted the same way. No screenshot and no re-snapshot are needed to know whether the action worked; take a screenshot afterwards only when the question is visual (layout, colours, a comparison against a reference). Several selectors combine with AND, `scopeRef` bounds the search to one container, and `includeHidden: false` excludes collapsed elements. Handles from an earlier snapshot are invalid after UI changes; selectors are not.
7. **Assert.** Presence, absence, text and the `{state}` tokens come from `uno_app_find_elements`; the tree shows bindings (`Text={Title}`), not current property values, so for a value the state group does not carry read the DataContext with `uno_app_get_element_datacontext` by selector. A screenshot is not how a state is read. Without that tool (Community), use the screenshot and the tree's text, and report DataContext assertions as not run. Save a screenshot of the final state.
8. **Report and clean up.** State each assertion with expected vs actual, attach screenshots, and `uno_app_close` on desktop unless the user wants the app left open. On failure, also capture a `detail: "full"` tree and the DataContext.

## Critical rules

- **Accessibility first, on every path.** Find controls in the element tree (`uno_app_find_elements` through the App MCP, or Windows UI Automation and Android `uiautomator` without it), act on them through their name, and assert on what the tree reports. A screenshot is a visual assertion or evidence, never the way to find a control or confirm its state while the tree can.
- **Act, then find; screenshot only for the eye.** The check that follows an action is `uno_app_find_elements` with `waitForMs` on the element whose state should have changed, about a hundred characters back. A screenshot after every click is the expensive habit this replaces: it costs an image in context each time and answers less. Screenshots remain for visual checks against a reference, for the before and after evidence of step 3 and step 8, and for the deliverables a task asks for.
- **Keep Studio's own UI out of the app.** Uno templates call `MainWindow.UseStudio();` under `#if DEBUG` in `App.xaml.cs`. With no arguments, the Hot Reload indicator and the Hot Design button sit over the app in every screenshot and under pointer clicks, and Hot Design opens by itself on the app's first launch, and on any launch after a session where it was active. Its designer and introduction overlay then cover the app: screenshots show the designer, pointer clicks land on it, and the visual tree does not show it. Before the first `uno_app_start`, the call should be `MainWindow.UseStudio(showHotReloadIndicator: false, launchHotDesignOnStart: false);`, still under `#if DEBUG`; Hot Reload and the App MCP keep working, so Debug screenshots are clean and there is no reason to capture from a Release build. In an app you created in this session, make the change and mention it in your report. In an existing app, ask the developer first, because it changes how their app starts under the debugger. If they decline, leave the call as it is, check the first screenshot for the Hot Design designer, and if it is there ask them to exit Hot Design in the app window; report any runtime check it blocked as not run. If Hot Design still opens, the `UNO_HOTDESIGN_LAUNCH` environment variable or the `UnoHotDesignLaunch` MSBuild property is set: both take precedence over the argument.
- **Edit the running app; start it again only for what Hot Reload cannot carry.** Once the app has been up for about 15 s, a change to an existing `.xaml` or `.cs` file reaches it through Hot Reload in 2 to 4 s, on desktop and Android alike; a C# edit recreates the current page, so navigate back to the state under test before asserting. After an edit, call `uno_app_hot_reload_status(file: "<edited file>")` when discovery lists it: it waits for that file's Hot Reload operation and says whether it was applied, with the compiler errors when it was not (fix those and save again; no restart). Then assert with `uno_app_find_elements(waitForMs)` on the element the change affects. Do not call `uno_app_start`: a restart costs 15 to 40 s plus the navigation back, and sessions that restarted after each edit made 17 to 29 starts. Start again only to change launch arguments, platform or app data, for a Release build, or after a change Hot Reload does not carry (a new file, the `.csproj`, packages, startup code in `App.xaml.cs`). A dropped edit is not carried by a later edit of another file. If the status says no operation covered the file, or without the tool the edit has not shown after about 10 s, check the file saved and edit that file again; if it still does not show, start the app.
- **One app instance, and close it before you build.** Build only when a start is needed (previous rule). A running app locks its `bin` folder, so `dotnet build` or another `uno_app_start` fails with `MSB3026`/`MSB3027` copy errors. `uno_app_close` first, and do not launch the app yourself with `dotnet run` or a script while the App MCP drives it.
- **Save screenshots to files; read one back only for a visual assertion.** Without `path` the image comes back in the tool result and stays in context for every later call. Save one before and after, on pass and on fail: that evidence makes the report reviewable and regressions diagnosable. To save a file, the path must be inside the App MCP's workspace, which is the selected solution's folder (`effectiveWorkspaceDirectory` in `uno_health`), and if the save fails with "Could not find a part of the path", create the folder and retry. Copy the file elsewhere afterwards if the task needs it there.
- **Selectors do not expire; handles do.** Act by `automationId` or `name` and nothing needs refreshing. When you must use a handle, any action that changes UI invalidates it: re-snapshot before the next interaction, and remember recycled `ListView` items change handles on scroll.
- **Never assert during a transient state.** A `ProgressRing`, `ProgressBar`, loading text, or disabled submit button means the async work is still running; poll until it clears, then assert. Asserting early produces false failures and false passes.
- **Selectors, then handles, then coordinates.** A selector is one call and survives everything; a handle survives until the next UI change; a coordinate click survives neither layout changes nor DPI differences. When coordinates are unavoidable, take a `detail: "full"` snapshot without `elementRef` and click the centre of the element's `@@x,y,w,h` bounds: the bounds are relative to the snapshot root, and clicks are relative to the window.
- **Give every control an automation id.** `AutomationProperties.AutomationId`, unique on its page, is the `automationId` selector here and UI Automation's `AutomationId` in Release verification; `x:Name` or `AutomationProperties.Name` is the `name` selector, shown as `#Name` in the tree, and the only thing Android's accessibility tree exposes (`content-desc`), so a control a test touches gets both when its text may vary. An element with neither is found only by text or position. In an app you created, add them as you write the XAML; in an existing app, suggest them.
- **Keep the default `detail: "compact"` or `"normal"`.** `"full"` adds framework nodes, bounds, and offscreen flags and is large; use it for coordinates and failure diagnosis. A hidden element (`!hidden`) only proves something is collapsed; never interact with it.
- **Be specific.** Assert exact text, counts, and enabled states rather than "element exists": `{items=12}`, `{checked}`, not `{disabled}`. Absence is `0 matched` with `includeHidden: false`.
- **Feed states are three assertions, not one.** For a `FeedView`, check the progress template appears, then the value or error template replaces it, then the bound data matches via DataContext.
