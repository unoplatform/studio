# OIDC and Web Sign-in on the Skia Desktop Head

Uno's own `WebAuthenticationBroker` is not implemented on the Skia desktop head (`net10.0-desktop`: Windows, macOS, Linux). Since **Uno.Extensions 8.0.0-dev.135** (uno.extensions #3261) `AddOidc` and `AddWeb` register one: `DesktopWebAuthenticationBrokerProvider`, which opens the sign-in page in the system browser and receives the redirect on a loopback HTTP listener. Verified with the Uno.Samples OIDC sample (`UI/Authentication.OidcExtensionsDemo`, Uno.Sdk 7.0.0-dev.89) and Web sample (`UI/Authentication.WebExtensionsDemo`, Uno.Sdk 7.0.0-dev.115).

## Which version the app is on

Check the Uno.Sdk in `global.json` before promising desktop sign-in: 7.0.0-dev.95 and later pin Uno.Extensions 8.0.0-dev.147 or later and need nothing more. An `UnoExtensionsVersion` in the csproj or `Directory.Build.props` overrides the pin. On an older Sdk, opt in or upgrade:

- Set `<UnoExtensionsVersion>8.0.0-dev.135</UnoExtensionsVersion>` **and** use Uno.Sdk 7.0.0-dev.89 or later: dev.135 was built against Uno.WinUI 7.0.0-dev.2428 and Toolkit 11.0.0-dev.155, and an older Sdk's pins fail the restore with NU1605 downgrade errors.
- From Uno.Sdk 7.0.0-dev.89 through at least 7.0.0-dev.115, a Debug build needs a `Uno.WinUI.Lottie` PackageReference (7.0.0-dev.1663, Debug-only item group) while the Hot Design tooling references `Uno.UI.Lottie` (uno.extensions #3262); without it the desktop app dies with `FileNotFoundException: Uno.UI.Lottie` or hangs with no window. Release builds do not need it.

## With the broker (8.0.0-dev.135 and later)

- The redirect URI must be a loopback HTTP address, `http://localhost:<port>/authentication-callback`; a custom scheme is not routed back to a desktop app. Register exactly that string and fix the port so it can be registered once. The listener binds the whole port and matches the path itself (on macOS `localhost` binds `::1`, which browsers reach).
- Give the desktop head its own redirect URIs through configuration, not code: `AddInMemoryCollection` entries for `OidcAuthentication:RedirectUri` and `:PostLogoutRedirectUri` in a `ConfigureAppConfiguration` call after the embedded appsettings (`references/oidc.md` explains why code options cannot override one value). The sample's `Platforms/Desktop/PlatformSupport.Desktop.cs` is that and nothing else.
- `AutoRedirectUriFromWebAuthenticationBroker()` works here too: `GetCurrentApplicationCallbackUri()` returns `http://localhost:{port}/authentication-callback` with a free port probed once per process, unless `WinRTFeatureConfiguration.WebAuthenticationBroker.DefaultReturnUri` pins it. Pin it: an identity provider needs one registered URI.
- Order matters: the registration goes through `ApiExtensibility`, where the first registration wins, and the static `WebAuthenticationBroker` keeps the provider it first resolved. Nothing may touch `WebAuthenticationBroker` (`GetCurrentApplicationCallbackUri()` included) before `UseAuthentication` has run, and an app that supplies its own `IWebAuthenticationBrokerProvider` must register it before. A sign-in that fails with an error naming `DesktopWebAuthenticationBrokerProvider.TryRegister()` is this case.
- Logs: the broker logs under `Uno.Extensions.Authentication` through Uno's logger, which `UseLogging` only connects with `enableUnoLogging: true` and whose `CoreLogLevel` hides it below Warning. `logBuilder.AddFilter("Uno.Extensions.Authentication", LogLevel.Information)` shows `WebAuthenticationBroker flows are handled by the desktop loopback broker (system browser + <callback>)` on the first flow; no such line means another provider handled it.
- Sign-out: the provider sends the cached ID token as `id_token_hint`, so the identity provider can redirect to the listener. Duende's demo server shows its logged-out page with a link that does, and `LogoutAsync` completes within seconds when the user follows it; no redirect within `WinRTFeatureConfiguration.WebAuthenticationBroker.AuthenticationTimeout` ends the flow as a timeout, and the tokens are cleared either way.
- `AddWeb` gets the same broker, but it does not tie the callback request to the flow it started and any local page or process can reach the listener: send a `state` from `PrepareLoginStartUri` and check it in `PostLogin` (`references/web.md`).
- Another browser (a private window, a specific one): derive from `DesktopWebAuthenticationBrokerProvider`, override `LaunchBrowserAsync`, and register the type with `ApiExtensibility.Register` before `AddOidc`, guarded by `#if !WINDOWS` (the type is absent from the WinAppSDK build).

## Before 8.0.0-dev.135

`AddOidc`'s `WebAuthenticatorBrowser` calls `WebAuthenticationBroker.AuthenticateAsync`, which throws `NotImplementedException`; the provider logs `Error logging in: System.NotImplementedException` and `LoginAsync` returns `false`. The workaround is your own `IBrowser` (`Duende.IdentityModel.OidcClient.Browser`) in the desktop head: open the system browser on `options.StartUrl`, listen with `HttpListener` on `options.EndUrl` (the configured redirect URI, so make it loopback), answer the one request with a small page, return `new BrowserResult { ResultType = Success, Response = context.Request.Url.OriginalString }`, and append `id_token_hint=<IdToken from ITokenCache>` to an end-session URL that lacks it, or `LogoutAsync` waits the whole 300 s. Register it with `services.AddTransient<IBrowser, SystemBrowser>()` in a `ConfigureServices` call placed **after** `UseAuthentication`: the last `IBrowser` registration wins, the opposite of the broker rule above. The Uno.Samples OIDC sample carried a working `Platforms/Desktop/SystemBrowser.cs` until it moved to dev.135; its git history up to commit `258cba3e` has it. The same configuration override applies.

`AddWeb` has no `IBrowser` seam, so there the only pre-dev.135 route is an `IWebAuthenticationBrokerProvider` of your own registered through `ApiExtensibility.Register` before `AddWeb`.
